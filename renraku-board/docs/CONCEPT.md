# 職員連絡ボード 構想書
## スプレッドシート × Google Apps Script（GAS）による実装構想

令和8年度・職員会議／打合せの「連絡事項」運用をウェブアプリ化するプロジェクトです。
現行のスプレッドシート（会議ごとにシートをコピーして運用）を、**1枚のデータベース＋GASウェブアプリ**の形に刷新します。

---

## 1. コンセプトと基本方針

### 1.1 何を作るか

会議で出た連絡事項を職員が**確認・対応し、その進捗（何名が対応済みか）が可視化される**ボード。

- **データベース**: Google スプレッドシート（`連絡事項` / `職員マスタ` / `確認ログ` / `会議` / `コメント` / `ピン` の6シート）
- **アプリ本体**: GAS ウェブアプリ（`HtmlService` による1画面SPA）
- **配信対象**: 学校の Google Workspace アカウント（全職員がログイン可能）

### 1.2 発想の転換 —「毎日シートを作る」から「1つのDBを切り出して見る」へ

現行は原本シートをコピーして日付シート（`0717職員会議`, `0709` …）を量産しているが、
ウェブアプリ化にあたり **連絡事項を1枚の `連絡事項` シートに1行1件で蓄積**し、
アプリ側が「未完了のみ」「7月分」「7/17会議の分」と切り出して表示する方式に変える。

| 現行の課題 | 本方式での解決 |
|---|---|
| シートが会議ごとに増え、探しにくい | シートは増えない。日付・会議はアプリのフィルタで切替 |
| 誰が読んだか分からない | ログインユーザーを自動識別し、確認・対応をワンタップ記録 |
| 対応漏れに気づけない | 期限・対象者・進捗率を表示し、未対応者を名前で可視化＋メール督促 |

> 要望①「毎日のシート自動生成」は、この方式では**不要**になる（シートを増やさず日付で切り出すため）。
> 印刷・記録用に従来レイアウトが必要な場合のみ、`exportMeetingSheet()` で会議単位の整形シートを書き出せる。

### 1.3 確定した運用方針（ヒアリング結果）

| 論点 | 決定 |
|---|---|
| 運用形態 | GAS ウェブアプリ中心 |
| アカウント | 全職員が学校 Google アカウントを保有 → **ログインユーザーを自動識別**（名前選択不要） |
| 対象範囲 | 会議アジェンダ（協議事項）も含めて全体刷新 |
| 職員数 | 21〜40名規模 |
| 会議中の記入 | **アプリの起票フォームから入力**（シート直書きはしない） |
| 未対応者の表示 | **全職員に名前を公開**（相互の声かけを促す） |
| リマインド手段 | **メール**（毎朝、期限超過の未対応者へ自動送信） |

### 1.4 GASの制約と設計判断

| 制約 | 対策 |
|---|---|
| 同時書き込みで行がずれる恐れ | 書き込みは `LockService` で直列化。行の特定はUUID（連絡ID）で行い行番号に依存しない |
| 確認記録の重複・取消 | `確認ログ` は (連絡ID×職員) で1行。状態列（済／取消）を更新する追記型 |
| 実行時間 6分/リクエスト | 1リクエスト＝1操作に細分化。集計は都度計算でも数百〜数千行なら軽量 |
| リアルタイムpush不可 | 進捗は画面を開いた時点＋操作時に再取得（頻繁なポーリングは不要） |
| 職員にシートを直接触らせたくない | ウェブアプリは「アクセスユーザーとして実行」でデプロイし、記録はアプリ経由のみ |

## 3. シート設計（データベース）

### 3.1 `連絡事項`（1行1件で蓄積）

| 列 | 内容 | 例 |
|---|---|---|
| ID | UUID（不変の主キー） | `a1b2c3…` |
| 会議ID | どの会議で出たか（`会議`シートと紐付け） | `M20260717` |
| 種別 | `協議` / `連絡` | `連絡` |
| No | 会議内での通し番号 | `4` |
| 議題 | 見出し | `端末の管理番号について` |
| 内容 | 本文 | `スズキ校務の詳細名簿に入力を…` |
| 発言者 | 氏名 | `横田` |
| 時間 | 分 | `1` |
| 資料 | 有無・種別 | `あり（データ）` |
| 資料リンク | URL | `https://…` |
| 期限 | 対応期限（空欄可） | `2026-07-24` |
| 要対応 | `TRUE`=要対応 / `FALSE`=閲覧のみ | `TRUE` |
| 対象区分 | `全員` / `担任` / `個別` | `全員` |
| 対象メール | 個別指定時のみ（カンマ区切り） | `a@…,b@…` |
| 掲載 | `TRUE`でボード掲載（会議確定時にON） | `TRUE` |
| 作成日時 | タイムスタンプ | |

### 3.2 `職員マスタ`（自己維持型）

| 列 | 内容 |
|---|---|
| 氏名 | 表示名（初回アクセス時に本人が入力） |
| メール | 学校アカウント（ログイン識別・督促宛先。自動取得） |
| 分掌 | 担任判定などに利用（`担任` を含むか等） |
| 表示順 | 登録順 |
| 在職 | `FALSE` は集計対象外 |
| 最終ログイン | 最後にアプリを開いた日時（自動更新） |

**担当者に依存しない維持の仕組み**（手入力を原則なくす）:

1. **初回アクセス時に自己登録** — 職員がアプリを初めて開くと、メールは自動取得され、
   名前（と担任かどうか）を一度入力するだけで名簿に加わる。新任も自動で増える。
2. **1ヶ月ログインの無い職員は自動で対象外** — `最終ログイン` が30日より前の職員は
   `activeStaff_()` の集計から除外（分母＝いま活動中の職員）。
3. **年度末（4/1早朝）に自動リセット** — `職員マスタ` を `職員マスタ_YYYY年度` に
   アーカイブしてから空にする。新年度は全員が開いて再登録＝分掌も含めて自動更新。

### 3.5 年度末アーカイブとパフォーマンス

アプリはボードを開くたびに `連絡事項`・`確認ログ` の全行を読むため、
データが数年分たまると読み込みが少しずつ遅くなる（1年分＝ログ数千行程度までは体感差なし）。

そこで 4/1 早朝の年度末処理（`yearEndReset`）では、職員マスタに加えて
**`連絡事項`・`確認ログ`・`会議` も「シート名_YYYY年度」へ丸ごと退避してから空にする**。

- 稼働シートは常に1年度分だけ → 何年運用しても読み込み時間が増えない
- 過去のデータはアーカイブシートにそのまま残る（削除しない）
- 同名のアーカイブが既にあれば退避はスキップ（誤って二重実行しても安全）
- 注意: 年度をまたいで対応させたい連絡（3月起票・4月期限など）は、
  リセット後に新年度分として起票し直す運用とする

> 補足: リセット直後の4月は、開いた職員から順に名簿が埋まるため、
> 全員がログインするまでは進捗率の分母が実数より小さく出る。
> 年度初めの職員会議で「全員ボードを開いて登録を」と一声かければ当日に揃う。

### 3.3 `確認ログ`（追記型・(連絡ID×職員×チェック種別)で1行）

| 列 | 内容 |
|---|---|
| 連絡ID | `連絡事項.ID` |
| メール | チェックした職員 |
| 氏名 | 表示用 |
| 状態 | `済` / `取消` |
| 更新日時 | タイムスタンプ |
| チェック種別 | `確認` / `対応`（空欄は旧データ＝当時のメインチェックとみなす） |

**チェックは2段階**:

- **要対応**の連絡 … 「**確認した**」（内容を見た）と「**対応済み**」（作業を終えた）を別々に記録。
  進捗バーは対応済み率、テキストに確認数も併記（例: 対応 18/31名（58%）・確認 25/31名）。
- **閲覧のみ**の連絡 … 「確認」のみ。

進捗率 ＝ （状態が`済`の対象職員数）÷（対象職員数）。未対応者 ＝ 対象職員のうち対応`済`のログが無い者。

### 3.4 `会議`

| 列 | 内容 |
|---|---|
| 会議ID | `M` + 日付 |
| 日付 | |
| 種別 | `職員会議` / `打合せ` |
| 名称 | 表示名 |

### 3.5 `コメント`（追記型・議題ごとの意見交換）

| 列 | 内容 |
|---|---|
| 連絡ID | `連絡事項.ID` |
| メール | 投稿した職員 |
| 氏名 | 表示用 |
| 本文 | 500文字まで |
| 投稿日時 | タイムスタンプ |

協議事項・連絡事項どちらにも投稿できる。全職員が閲覧・投稿でき、編集・削除は無い
シンプルな仕組み（誤解を招く投稿は口頭やチャットで解決する運用を想定）。
一覧では投稿数だけを軽量に表示し、モーダルを開いたときに内容を取得する。

### 3.6 `ピン`（個人ごとの目印）

| 列 | 内容 |
|---|---|
| 連絡ID | `連絡事項.ID` |
| メール | ピン留めした職員（1人1連絡につき最大1行） |
| 日時 | タイムスタンプ |

**ピンは個人的な目印であり、他の職員からは見えない**（進捗の集計にも一切関与しない）。

サイドバーの「自分の未対応」が拾うのは `要対応 かつ 自分が対象 かつ 未対応` の連絡だけで、
次のものはどの導線にも乗らない。ピンはこの隙間を埋めるために用意した。

- 閲覧のみの連絡（時程表・要項など、対応は不要だが何度も見返したいもの）
- 自分が対象外だが把握しておきたい連絡
- すでに対応済みだが手元に置いておきたい連絡（チェックすると折りたたまれて消える）
- 期限が無く、日付順の導線に乗らない連絡

つまり「タスク管理（未対応かどうか）」と「参照（自分にとって重要かどうか）」は別の軸であり、
ピンは後者を担当する。

## 4. 画面構成（ウェブアプリ）

PC横長画面に最適化した1画面SPA。上部にタブ＋本文（可変幅）、右に固定幅のサイドバーを
常時表示する2カラム構成（画面が狭いときはサイドバーが下に回り込む）。

| タブ | 役割 |
|---|---|
| **連絡ボード** | すべての連絡を**1本の連続リスト**で表示（月が新しい順 → 重要 → 要対応 → 期限が近い順）。表示範囲は**対応状況フィルタ**で切り替える（既定は「未完了のみ」）。月の絞り込みはプルダウンで行う |
| **会議** | 会議を選び、協議事項＋連絡事項をアジェンダ表で表示。時間合計を自動計算。会議中の投影にも使える |
| **確認状況** | **自分が発信した**要対応の連絡について、進捗率と**未対応者の氏名一覧**を期限の近い順に表示 |

> **タブを3つに整理した理由**（旧構成は5タブ）
> 旧「今日のボード／完了した連絡」の分かれ目は「対象者全員が対応したか」だったため、
> ある連絡がどちらにあるかを本人が予測できず（他人の対応状況で決まるため）、
> 探すときに2つのタブを行き来する必要があった。1つのタブ＋状態フィルタに統合し、
> 「探すときは1箇所で全件から探せる」ようにした。
> 「自分の未対応」タブは右サイドバーに常時表示されるようになったため廃止した。

> **月ごとの開閉セクションを廃止した理由**
> 月の絞り込みプルダウンと役割が重複していた。加えて、月ヘッダー（約52px）と
> 各月の中の「要対応」「閲覧のみ」見出し（約54px×2）で**1か月あたり約180px**を消費し、
> 絞り込みバーと統計カード3枚（約134px）と合わせると、最初のカードが出るまでに
> 約240pxの枠が積まれていた。ノートPC（縦768px）ではカードが1〜2枚しか見えない。
> 「要対応／閲覧のみ」の区別はカードのチップと並び順で分かるため、見出しごと廃止し、
> 統計は1枚のカード（後述の概況カード）に統合した。

> **概況の数字をタブにしなかった理由**
> 「掲載中／期限が今日・超過／あなたの未対応」をワンクリックで絞り込めるようにしたいという
> 要望があり、独立したタブ列（4つ目のナビゲーション軸）にする案も検討した。しかし
> 「未対応」を独立タブにすると、対応した瞬間にその連絡がタブから消えてしまい、これは
> かつて「今日のボード／完了した連絡」を廃止した理由（対象者の状態で自動的に居場所が
> 変わり、本人が予測できない）とまったく同じ問題を再発させる。加えて上部タブ
> （連絡ボード／会議／確認状況）と並んで「タブが2列」になり、かえって窮屈になる。
> そこで、既存の連絡ボードタブの中で完結する**1枚のクリック可能な概況カード**にした。
> 各区画（`.stat-seg`）はそれぞれボタンで、押すとその条件だけへ一発絞り込みできる
> （もう一度押すと解除）。ナビゲーションの軸を増やさずに、ワンクリックという分かりやすさは
> 確保できる。
> 現在は5区画（掲載中／期限が今日・超過／未対応／確認・対応済／★ピン留め）。
> 「未対応」と「確認・対応済」が対になっていて、自分の進み具合が数字のまま見える。
> ラベルに「あなたの」は付けない（5つ並ぶと横に伸びすぎるため）。誰の話かは
> 各ボタンの `title` 属性（ホバーで出る説明）が補う。

- **対応状況フィルタ**: 「未完了のみ」（既定）／「すべて」／「完了のみ」。
  日常は未完了だけが見えて集中でき、探すときは「すべて」にすれば全件から検索できる。
  なお「自分の済みを折りたたむ」動作は**「未完了のみ」表示のときだけ**働く
  （完了を含む表示で畳むと、ほぼ全件が隠れて空に見えてしまうため）。
- **絞り込み**: 対応状況のほかに3つの条件を組み合わせられる。
  **キーワード検索**（議題・内容・発信者、入力の少し後に自動で絞り込み）、
  **月選択**（連絡が紐づく会議日、会議なしは作成日。**初期表示は現在の月**を選んでおく。
  対象月に連絡が無ければ自動的に「すべての月」にフォールバックする）、
  **発信者選択**（表示中の母集団から動的に生成。氏名の後ろに件数を表示し、五十音順で並べる）。
  「クリア」ですべて解除（対応状況も既定の「未完了のみ」、月も「すべての月」に戻る。
  現在の月が0件のときに「クリア」を押しても何も変わらない、という事態を避けるため、
  月はあえて「現在の月」ではなく「すべての月」に戻す）。
  絞り込んで0件になったときは「絞り込みを解除する」ボタンを出す。
- **連絡の通し番号**: 連絡事項（kind=連絡）には、**月ごとに1からリセットされる番号**
  （No.1, No.2…）が自動で付く。カードの先頭に丸いバッジで表示され、会議アジェンダの
  「連絡事項」表の No. 列にも同じ番号が出る（協議事項は従来どおり会議内の通し番号）。
  「5番を見てください」のように、打ち合わせで口頭でも指し示しやすくするための番号で、
  並べ替えや削除では変わらない（シート上の追加順で確定するため、行を並べ替えない限り安定）。
  - 番号が月ごとに戻る以上、月をまたいで並べると「何月の5番か」が分からなくなる。
    そのため**表示中の連絡が2か月以上にまたがるときだけ**、細い月の区切りを挟む
    （罫線＋ラベルのみで開閉ボタンは無い）。1か月しか出ていないときは曖昧さが無いので出さない。

### 4.1 右サイドバー（常時表示）

| 部品 | 役割 |
|---|---|
| **ミニカレンダー** | 月送り（‹ ›）付き。日付の下に**緑ドット＝その日に追加された連絡**、**赤ドット＝その日が期限の連絡**を表示。今日の日付は塗りつぶし。**常に最上部**に置く（下のピン留めパネルは件数0で消えるため、下に置くとカレンダーの位置が上下してしまう） |
| **★ピン留めリスト** | 自分がピン留めした連絡の一覧。**絞り込みの状態に関係なく常に全件**を出す。ピンが0件のときはパネルごと隠す |
| **自分の未対応リスト** | 自分が対象で未対応の連絡を**期限が近い順**に一覧。番号・議題・期限を表示（タブを開かずに常に見られるため、旧「自分の未対応」タブは廃止した） |

- **ジャンプ**: カレンダーの**日付のマスをクリック**すると、その日に追加された連絡と
  その日が期限の連絡の**両方**へまとめて移動する。移動時は絞り込みを解除し、必要なら月セクションと
  「自分の済み」の折りたたみを自動で開き、スクロール＋一瞬ハイライトで位置を示す。対象が
  すべて完了済みの場合は対応状況フィルタを「すべて」に切り替えて見えるようにする。サイドバーのリストも同じ動きをする。
  - 日付のマスは `<button>` で、キーボードでも辿れる。緑・赤のドットは**状態を示す印**であり
    押せる要素ではない（6pxのドットは狙いにくく、ボタンの入れ子はHTMLで許されないため）。
- **予定のホバー表示**: 日付にカーソルを乗せると、その日の**共有Googleカレンダーの予定**を
  ツールチップで表示する。Apps Scriptの**スクリプト プロパティ**に `SHARED_CALENDAR_ID` を
  設定したときだけ有効（未設定・権限なし・ID誤りの場合は、ツールチップが出ないだけで他は
  正常に動く）。`sharedCalendarId_()` がこれを読む。
  - `Code.gs` に直接書かないのは、学校ごとに異なるこの値をコードに混ぜると、コード更新
    のたびに `git pull` が「ローカルの変更を消してよいか」で止まってしまうため。
    スクリプト プロパティはコードと切り離してGoogle側に保存されるので影響しない。
  予定は月の表示・切替時に1回だけ取得してクライアント側にキャッシュする（ホバーのたびに
  サーバーへ問い合わせない）。

- **カラーテーマ**: 自動（OS設定）／ライト／ダークを切替（ブラウザに保存）。
- **チェックの応答性**: ボタンは押した瞬間に画面へ反映し、保存はバックグラウンドで実行
  （楽観的更新）。連続して次々チェックできる。保存に失敗したときだけ表示を巻き戻して通知。
  サーバー側も、記録時の全体再集計を省き、職員マスタの読込を1回に統合、
  最終ログインの書込を1時間1回に間引くなど読み書きを最小化している。
- **起票後の即時表示**: 連絡を追加すると、`submitItem` が追加した連絡（と新規作成した
  会議があればその情報）を整形して返し、画面はそれをその場のデータに差し込んで
  現在の画面だけを再描画する。一覧を丸ごと再読込（`getInitialData` の再実行）はしない。
- **他の職員による更新の反映**: GASのウェブアプリにはサーバーから画面へ知らせる
  プッシュ通知の仕組みが無いため、**60秒ごとの自動ポーリング**＋**手動の更新ボタン**で
  新着を取り込む。自分の保存が進行中の間や、起票・登録フォームを開いている間は
  自動ポーリングを止めて操作の邪魔をしない。ブラウザのタブが背面のときは
  自動ポーリング自体を休止し（クォータ節約）、タブに戻った瞬間に1回だけ確認する。
  - **更新カウンタで軽くする**: 毎回 `getInitialData()` を呼ぶと、年度末規模
    （連絡420件・確認ログ19,530行・職員31名）で1回あたり約13万セルの読み取りになる
    （うち86%が確認ログ。連絡数×職員数×チェック種別数で増えるため一番速く膨らむ）。
    そこで書き込みのたびにスクリプトプロパティの `BOARD_VERSION` を+1し、
    自動ポーリングは**シートを読まない** `getBoardVersion()` だけを見て、
    値が変わったときにだけ本体を取りに行く。上記の規模で1日の累計読み取りが
    **約88%減**る。手動の更新ボタンは押した手応えを保つため常に本体を取得する。
    ピン留めは自分にしか見えない変更なのでカウンタを上げない（他の職員に
    無用な再読込をさせないため）。
- **起票**: 右下「＋連絡を追加」→ フォームで入力。
  - **会議**: 既存から選択／その場で新規追加／紐づけない（＝連絡ボードに直接掲載）。
  - **対象**: 全員／担任のみ／**個別（職員マスタから選択）**。
  - **資料リンク**: 最大3件まで追加可。Google Drive のリンクや画像URLは、カード右側の
    資料カラムに**サムネイル表示**（1件でも3件でも同じ180×72の固定サイズ・左詰め、
    クリックで原本を開く）。サムネイルを取得できない場合（閲覧権限なし・非対応形式）は
    自動的に「📄 資料①」のテキストリンクに切り替わる。
- **編集**: 発信者本人は、板・会議アジェンダ双方に表示される✏️編集ボタンから、
  起票済みの議題・連絡をあとから修正できる（会議への紐づけと種別は編集不可、
  起票し直しで対応）。作成者メールが記録されていない旧データは誰でも編集可能。
- **コメント**: 各議題・連絡に💬コメントボタン。全職員が自由に意見を書き込め、
  未読の目安として件数バッジが常時表示される。
- **重要**: 起票フォームの「⚠️ 重要」にチェックを入れると、カードが赤く強調され
  （左に太い赤帯＋淡い赤の下地＋「⚠️ 重要」チップ）、月セクションの先頭に並ぶ。
  ピン留めが*個人の*目印なのに対し、重要は*発信者が全員に向けて示す*印なので併用できる。
- **ピン留め**: 各カードの★ボタンで、自分だけの目印を付けられる（他の職員には見えない）。
  留めた連絡はサイドバー（カレンダーの下）に常時表示され、**概況カードの「★ ピン留め」区画**を押すと
  本体のカード表示に切り替えられる。
  - ピンは**完了済みの連絡にも付けられる**ため、ONにすると対応状況を自動的に「すべて」へ
    広げる（既定の「未完了のみ」のままだと、留めたはずの連絡が出てこないため）。
    サイドバーのリストは絞り込みと無関係に常に全件出す。
  - ほか 議題・内容・種別・期限・要対応 を入力。
- モックアップ: [`../mockups/board.html`](../mockups/board.html)（実データを用いた操作可能なプロトタイプ）

## 5. サーバー関数（`src/Code.gs`）

| 関数 | 役割 |
|---|---|
| `doGet(e)` | `Index.html` を配信 |
| `setup()` | 6シートとヘッダー・サンプルデータを生成（初回のみ手動実行） |
| `getInitialData()` | ログインユーザー情報＋会議一覧＋掲載中の連絡（自分のチェック状況・進捗付き）を返す。併せて本人の最終ログインを更新 |
| `registerMe(name, isHomeroom)` | 初回アクセス時の自己登録（氏名・担任区分を職員マスタへ） |
| `yearEndReset()` | 毎朝チェックし、4/1のみ6シート（職員マスタ・連絡事項・確認ログ・会議・コメント・ピン）をアーカイブして空にする |
| `recordCheck(itemId, done, checkType)` | 確認／対応のログを追記・更新（`LockService`）。新しい進捗を返す |
| `submitItem(payload)` | 連絡・協議事項を1件追加（起票フォーム）。追加した連絡と新規会議を返し、画面はその場に反映 |
| `getMeetingAgenda(meetingId)` | 指定会議の協議事項＋連絡事項を返す（編集可否・コメント数・連絡の月番号付き） |
| `buildMonthNoMap_(meetingDates)` | （内部）連絡事項に月ごとの通し番号を振る。シート行順＝追加順として扱う |
| `editItem(itemId, payload)` | 起票済みの議題・連絡を編集（発信者のみ／会議・種別は変更不可） |
| `getUncheckedNames(itemId)` | 未対応者の氏名一覧を返す（全員閲覧可） |
| `getComments(itemId)` / `addComment(itemId, text)` | コメントの取得・投稿（全員可） |
| `togglePin(itemId, pinned)` | 自分のピン留めのON/OFF（1人1連絡につき最大1行。他の職員には見えない） |
| `getCalendarEventsForMonth(ym)` | 共有カレンダーの予定を日付ごとに返す（ホバー表示用。未設定・失敗時は空） |
| `sendReminders()` | 毎朝の時間トリガー。期限超過の未対応者へメール督促 |
| `installTriggers()` | 督促トリガーを登録（初回のみ手動実行） |
| `exportMeetingSheet(meetingId)` | （任意）従来レイアウトの会議シートを書き出す |

## 7. セットアップ手順（概要）

1. スプレッドシートを新規作成し、拡張機能 → Apps Script を開く。
2. `src/` の `Code.gs` と `Index.html` を貼り付け（または clasp で push）。
3. エディタで `setup()` を1回実行 → 4シートとサンプルが生成される。
4. `職員マスタ` に実際の職員（氏名・メール）を入力。
5. デプロイ → ウェブアプリ。「次のユーザーとして実行: **アクセスしているユーザー**」「アクセスできるユーザー: **組織内の全員**」。
6. エディタで `installTriggers()` を1回実行 → 毎朝の督促メールが有効化。
7. 発行されたURLを職員に共有（ブックマーク推奨）。

詳細は [`../src/README.md`](../src/README.md) を参照。
