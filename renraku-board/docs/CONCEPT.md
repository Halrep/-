# 職員連絡ボード 構想書
## スプレッドシート × Google Apps Script（GAS）による実装構想

令和8年度・職員会議／打合せの「連絡事項」運用をウェブアプリ化するプロジェクトです。
現行のスプレッドシート（会議ごとにシートをコピーして運用）を、**1枚のデータベース＋GASウェブアプリ**の形に刷新します。

---

## 1. コンセプトと基本方針

### 1.1 何を作るか

会議で出た連絡事項を職員が**確認・対応し、その進捗（何名が対応済みか）が可視化される**ボード。

- **データベース**: Google スプレッドシート（`連絡事項` / `職員マスタ` / `確認ログ` / `会議` の4シート）
- **アプリ本体**: GAS ウェブアプリ（`HtmlService` による1画面SPA）
- **配信対象**: 学校の Google Workspace アカウント（全職員がログイン可能）

### 1.2 発想の転換 —「毎日シートを作る」から「1つのDBを切り出して見る」へ

現行は原本シートをコピーして日付シート（`0717職員会議`, `0709` …）を量産しているが、
ウェブアプリ化にあたり **連絡事項を1枚の `連絡事項` シートに1行1件で蓄積**し、
アプリ側が「今日のボード」「7/17会議の分」と切り出して表示する方式に変える。

| 現行の課題 | 本方式での解決 |
|---|---|
| シートが会議ごとに増え、探しにくい | シートは増えない。日付・会議はアプリのフィルタで切替 |
| 誰が読んだか分からない | ログインユーザーを自動識別し、確認・対応をワンタップ記録 |
| 対応漏れに気づけない | 期限・対象者・進捗率を表示し、未対応者を名前で可視化＋メール督促 |

> 要望①「毎日のシート自動生成」は、この方式では**不要**になる（シートを増やさず日付で切り出すため）。
> 印刷・記録用に従来レイアウトが必要な場合のみ、`exportMeetingSheet()` で会議単位の整形シートを書き出せる。

### 1.3 確定した運用方針（ヒアリング結果）

| 論点 | 決定 |
|---|---|
| 運用形態 | GAS ウェブアプリ中心 |
| アカウント | 全職員が学校 Google アカウントを保有 → **ログインユーザーを自動識別**（名前選択不要） |
| 対象範囲 | 会議アジェンダ（協議事項）も含めて全体刷新 |
| 職員数 | 21〜40名規模 |
| 会議中の記入 | **アプリの起票フォームから入力**（シート直書きはしない） |
| 未対応者の表示 | **全職員に名前を公開**（相互の声かけを促す） |
| リマインド手段 | **メール**（毎朝、期限超過の未対応者へ自動送信） |

### 1.4 GASの制約と設計判断

| 制約 | 対策 |
|---|---|
| 同時書き込みで行がずれる恐れ | 書き込みは `LockService` で直列化。行の特定はUUID（連絡ID）で行い行番号に依存しない |
| 確認記録の重複・取消 | `確認ログ` は (連絡ID×職員) で1行。状態列（済／取消）を更新する追記型 |
| 実行時間 6分/リクエスト | 1リクエスト＝1操作に細分化。集計は都度計算でも数百〜数千行なら軽量 |
| リアルタイムpush不可 | 進捗は画面を開いた時点＋操作時に再取得（頻繁なポーリングは不要） |
| 職員にシートを直接触らせたくない | ウェブアプリは「アクセスユーザーとして実行」でデプロイし、記録はアプリ経由のみ |

## 3. シート設計（データベース）

### 3.1 `連絡事項`（1行1件で蓄積）

| 列 | 内容 | 例 |
|---|---|---|
| ID | UUID（不変の主キー） | `a1b2c3…` |
| 会議ID | どの会議で出たか（`会議`シートと紐付け） | `M20260717` |
| 種別 | `協議` / `連絡` | `連絡` |
| No | 会議内での通し番号 | `4` |
| 議題 | 見出し | `端末の管理番号について` |
| 内容 | 本文 | `スズキ校務の詳細名簿に入力を…` |
| 発言者 | 氏名 | `横田` |
| 時間 | 分 | `1` |
| 資料 | 有無・種別 | `あり（データ）` |
| 資料リンク | URL | `https://…` |
| 期限 | 対応期限（空欄可） | `2026-07-24` |
| 要対応 | `TRUE`=要対応 / `FALSE`=閲覧のみ | `TRUE` |
| 対象区分 | `全員` / `担任` / `個別` | `全員` |
| 対象メール | 個別指定時のみ（カンマ区切り） | `a@…,b@…` |
| 掲載 | `TRUE`でボード掲載（会議確定時にON） | `TRUE` |
| 作成日時 | タイムスタンプ | |

### 3.2 `職員マスタ`（自己維持型）

| 列 | 内容 |
|---|---|
| 氏名 | 表示名（初回アクセス時に本人が入力） |
| メール | 学校アカウント（ログイン識別・督促宛先。自動取得） |
| 分掌 | 担任判定などに利用（`担任` を含むか等） |
| 表示順 | 登録順 |
| 在職 | `FALSE` は集計対象外 |
| 最終ログイン | 最後にアプリを開いた日時（自動更新） |

**担当者に依存しない維持の仕組み**（手入力を原則なくす）:

1. **初回アクセス時に自己登録** — 職員がアプリを初めて開くと、メールは自動取得され、
   名前（と担任かどうか）を一度入力するだけで名簿に加わる。新任も自動で増える。
2. **1ヶ月ログインの無い職員は自動で対象外** — `最終ログイン` が30日より前の職員は
   `activeStaff_()` の集計から除外（分母＝いま活動中の職員）。
3. **年度末（4/1早朝）に自動リセット** — `職員マスタ` を `職員マスタ_YYYY年度` に
   アーカイブしてから空にする。新年度は全員が開いて再登録＝分掌も含めて自動更新。

### 3.5 年度末アーカイブとパフォーマンス

アプリはボードを開くたびに `連絡事項`・`確認ログ` の全行を読むため、
データが数年分たまると読み込みが少しずつ遅くなる（1年分＝ログ数千行程度までは体感差なし）。

そこで 4/1 早朝の年度末処理（`yearEndReset`）では、職員マスタに加えて
**`連絡事項`・`確認ログ`・`会議` も「シート名_YYYY年度」へ丸ごと退避してから空にする**。

- 稼働シートは常に1年度分だけ → 何年運用しても読み込み時間が増えない
- 過去のデータはアーカイブシートにそのまま残る（削除しない）
- 同名のアーカイブが既にあれば退避はスキップ（誤って二重実行しても安全）
- 注意: 年度をまたいで対応させたい連絡（3月起票・4月期限など）は、
  リセット後に新年度分として起票し直す運用とする

> 補足: リセット直後の4月は、開いた職員から順に名簿が埋まるため、
> 全員がログインするまでは進捗率の分母が実数より小さく出る。
> 年度初めの職員会議で「全員ボードを開いて登録を」と一声かければ当日に揃う。

### 3.3 `確認ログ`（追記型・(連絡ID×職員×チェック種別)で1行）

| 列 | 内容 |
|---|---|
| 連絡ID | `連絡事項.ID` |
| メール | チェックした職員 |
| 氏名 | 表示用 |
| 状態 | `済` / `取消` |
| 更新日時 | タイムスタンプ |
| チェック種別 | `確認` / `対応`（空欄は旧データ＝当時のメインチェックとみなす） |

**チェックは2段階**:

- **要対応**の連絡 … 「**確認した**」（内容を見た）と「**対応済み**」（作業を終えた）を別々に記録。
  進捗バーは対応済み率、テキストに確認数も併記（例: 対応 18/31名（58%）・確認 25/31名）。
- **閲覧のみ**の連絡 … 「確認」のみ。

進捗率 ＝ （状態が`済`の対象職員数）÷（対象職員数）。未対応者 ＝ 対象職員のうち対応`済`のログが無い者。

### 3.4 `会議`

| 列 | 内容 |
|---|---|
| 会議ID | `M` + 日付 |
| 日付 | |
| 種別 | `職員会議` / `打合せ` |
| 名称 | 表示名 |

## 4. 画面構成（ウェブアプリ）

PC横長画面に最適化した1画面SPA。上部にタブ、本文に連絡カードを縦1列で幅広表示。

| タブ | 役割 |
|---|---|
| **今日のボード** | 掲載中の連絡を「要対応（期限が近い順）／閲覧のみ」に分けてカード表示。進捗バー・チェックボタン |
| **会議** | 会議を選び、協議事項＋連絡事項をアジェンダ表で表示。時間合計を自動計算。会議中の投影にも使える |
| **自分の未対応** | 自分が対象で未チェックの連絡だけを抽出（本人視点の残タスク） |
| **確認状況（発信者用）** | 進捗率と**未対応者の氏名一覧**を表示し、任意で督促メールを送信 |

- **カラーテーマ**: 自動（OS設定）／ライト／ダークを切替（ブラウザに保存）。
- **チェックの応答性**: ボタンは押した瞬間に画面へ反映し、保存はバックグラウンドで実行
  （楽観的更新）。連続して次々チェックできる。保存に失敗したときだけ表示を巻き戻して通知。
  サーバー側も、記録時の全体再集計を省き、職員マスタの読込を1回に統合、
  最終ログインの書込を1時間1回に間引くなど読み書きを最小化している。
- **起票後の即時表示**: 連絡を追加すると、`submitItem` が追加した連絡（と新規作成した
  会議があればその情報）を整形して返し、画面はそれをその場のデータに差し込んで
  現在の画面だけを再描画する。一覧を丸ごと再読込（`getInitialData` の再実行）はしない。
- **他の職員による更新の反映**: GASのウェブアプリにはサーバーから画面へ知らせる
  プッシュ通知の仕組みが無いため、**60秒ごとの自動ポーリング**＋**手動の更新ボタン**で
  新着を取り込む。自分の保存が進行中の間や、起票・登録フォームを開いている間は
  自動ポーリングを止めて操作の邪魔をしない。ブラウザのタブが背面のときは
  自動ポーリング自体を休止し（クォータ節約）、タブに戻った瞬間に1回だけ確認する。
- **起票**: 右下「＋連絡を追加」→ フォームで入力。
  - **会議**: 既存から選択／その場で新規追加／紐づけない（＝今日のボードに直接掲載）。
  - **対象**: 全員／担任のみ／**個別（職員マスタから選択）**。
  - **資料リンク**: 最大3件まで追加可。
  - ほか 議題・内容・種別・期限・要対応 を入力。
- モックアップ: [`../mockups/board.html`](../mockups/board.html)（実データを用いた操作可能なプロトタイプ）

## 5. サーバー関数（`src/Code.gs`）

| 関数 | 役割 |
|---|---|
| `doGet(e)` | `Index.html` を配信 |
| `setup()` | 4シートとヘッダー・サンプルデータを生成（初回のみ手動実行） |
| `getInitialData()` | ログインユーザー情報＋会議一覧＋掲載中の連絡（自分のチェック状況・進捗付き）を返す。併せて本人の最終ログインを更新 |
| `registerMe(name, isHomeroom)` | 初回アクセス時の自己登録（氏名・担任区分を職員マスタへ） |
| `yearEndReset()` | 毎朝チェックし、4/1のみ4シート（職員マスタ・連絡事項・確認ログ・会議）をアーカイブして空にする |
| `recordCheck(itemId, done, checkType)` | 確認／対応のログを追記・更新（`LockService`）。新しい進捗を返す |
| `submitItem(payload)` | 連絡・協議事項を1件追加（起票フォーム）。追加した連絡と新規会議を返し、画面はその場に反映 |
| `getMeetingAgenda(meetingId)` | 指定会議の協議事項＋連絡事項を返す |
| `getUncheckedNames(itemId)` | 未対応者の氏名一覧を返す（全員閲覧可） |
| `sendReminders()` | 毎朝の時間トリガー。期限超過の未対応者へメール督促 |
| `installTriggers()` | 督促トリガーを登録（初回のみ手動実行） |
| `exportMeetingSheet(meetingId)` | （任意）従来レイアウトの会議シートを書き出す |

## 7. セットアップ手順（概要）

1. スプレッドシートを新規作成し、拡張機能 → Apps Script を開く。
2. `src/` の `Code.gs` と `Index.html` を貼り付け（または clasp で push）。
3. エディタで `setup()` を1回実行 → 4シートとサンプルが生成される。
4. `職員マスタ` に実際の職員（氏名・メール）を入力。
5. デプロイ → ウェブアプリ。「次のユーザーとして実行: **アクセスしているユーザー**」「アクセスできるユーザー: **組織内の全員**」。
6. エディタで `installTriggers()` を1回実行 → 毎朝の督促メールが有効化。
7. 発行されたURLを職員に共有（ブックマーク推奨）。

詳細は [`../src/README.md`](../src/README.md) を参照。
